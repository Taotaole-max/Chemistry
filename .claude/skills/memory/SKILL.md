# 项目记忆

## 为什么需要它

不同的 Claude Code 会话之间**不共享任何对话历史**：

- 本地 CLI 会话、云端 web 会话、不同机器上的会话，各自从零开始
- 云端容器是临时的，会话结束即销毁，没提交的东西全部丢失

唯一横跨所有会话的持久载体是**这个 git 仓库**。所以"记忆"= 仓库里的文件。写进去并推送 = 记住了；只存在对话里 = 必然丢失。

## 记忆存放在哪

| 文件 | 内容 | 加载方式 |
|---|---|---|
| `CLAUDE.md`（仓库根目录） | 索引 + 项目约定 + 当前状态。保持精简（150 行以内） | 每次会话**自动加载** |
| `.claude/memory/decisions.md` | 做过的技术决策和理由 | 被 CLAUDE.md 用 `@` 导入，自动加载 |
| `.claude/memory/gotchas.md` | 踩过的坑、环境怪癖、走不通的路 | 被 CLAUDE.md 用 `@` 导入，自动加载 |
| `.claude/memory/journal.md` | 按时间倒序的会话日志 | 按需读取（会越长越长，不自动加载） |

前三个文件必须保持小。它们每次会话都占上下文，臃肿了就是纯粹的浪费。日志可以随便长。

## 动作一：回忆

会话开始，或者用户提到"上次""之前""继续做"的时候：

1. `CLAUDE.md` 和被它导入的两个文件通常已经在上下文里了，先确认一下有没有
2. 需要时间线时，读 `.claude/memory/journal.md` 的**最上面几条**（倒序，最新在前），不要整篇读
3. 需要具体改了什么代码，用 `git log --oneline -20`——日记不重复记录 diff，git 已经记了

## 动作二：记录

**什么时候写**：做完一件有结论的事之后就写，不要攒到会话末尾——云端会话可能在你写之前就被回收了。具体时机是：

- 定下了一个会影响后续工作的技术选择
- 踩到了一个下次还会踩的坑
- 完成了一个阶段性的东西（跑通一个模型、加了一个 project）
- 用户明确说"记一下"

**写进哪个文件**：

- 决策（为什么选 A 不选 B）→ `decisions.md`
- 坑（这么干会失败 / 这个环境有个怪癖）→ `gotchas.md`
- 发生了什么（时间线）→ `journal.md` 顶部追加
- 影响到日常操作的约定、或者上面文件的新入口 → 更新 `CLAUDE.md`

**判断标准 —— 只写会改变未来行动的东西**：

写：
- 为什么选了这个方案，以及否决了什么
- 数据从哪来、放在哪、有什么坑（比如 API key 怎么配、某个数据集有脏值）
- 试过但失败的路（这是最值钱的，能省下未来重复踩坑的时间）
- 用户表达过的偏好（"我看不懂英文注释""模型别用 GPU"）

不写：
- 改了哪几行代码 —— git diff 已经记了，重复记只会过期
- 读一遍代码就知道的事实（有哪些函数、目录结构）
- 过程性的碎碎念（"我先试了 X 然后又试了 Y"），只留结论

**日记条目格式**（追加到 `journal.md` 顶部，最新在最上面）：

```markdown
## 2026-08-13 · 云端会话

**做了**：一句话说清楚。

**学到**：下次会用得上的事实。没有就删掉这行。

**下一步**：留给下个会话的接力棒。没有就删掉这行。
```

标注会话来源（`云端会话` / `本地会话`），因为坑往往和环境绑定。

## 动作三：提交并推送

**记忆没推送 = 没记住。** 写完文件立刻：

```bash
git add CLAUDE.md .claude/memory/
git commit -m "memory: <一句话说明记了什么>"
git push -u origin <当前分支>
```

关键点：**记忆只有合并到 `main` 之后才算真正共享**。新会话（尤其云端）是从默认分支全新 clone 的，躺在功能分支上的记忆别的会话看不见。所以记忆类改动要么直接提交到 `main`，要么尽快合并过去，别让它在分支上过夜。

## 冲突处理

`journal.md` 是顶部追加的，两个会话同时写会在文件开头冲突。**解决办法永远是两边都保留**，按日期排好序。不要丢弃任何一方的条目——那是另一个会话唯一的记录。

`decisions.md` 和 `gotchas.md` 冲突时要看内容：如果新决策推翻了旧决策，不要删掉旧的，在旧条目下面标注"已被 YYYY-MM-DD 的决策取代"，理由和结论一样有价值。
